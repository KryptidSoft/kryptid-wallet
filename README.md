### Kryptid Wallet (Multi-Chain Modular Edition)

Purely functional, client-side, non-custodial wallet for Bitcoin, Ethereum, Litecoin, Dogecoin, Binance Smart Chain, TRON, and Toncoin. Monero (XMR) architecture is pre-implemented under the hood and safely hidden for future deployment. Developed with zero cloud dependencies and no Node.js using Notepad++ and PowerShell. Built on a data-driven, polymorphic architecture that categorizes assets into cryptographic families (UTXO, EVM, TRON, TON, MONERO) to eliminate code duplication and scale infinitely without UI modifications. 

### 🚀 CURRENT ARCHITECTURE & COMPONENT STATUS

* **index.html**: Production user interface in English. Slipped into a fully data-driven, state-reactive model using uniform .crypto-card blocks equipped with data-coin attributes. Contains a prominent visual legal Disclaimer, an alphabetical multi-fiat dropdown (11 currencies + physical gold XAU), a dynamic universal transaction form (#action-zone) with a single re-rendering button (#universalSendBtn), and a strict production Content Security Policy (CSP) expanded to cover active Web3 network RPC endpoints. (Monero UI element is safely commented out for version v1.0).
* **main.js (Root)**: Core cryptographic engine (CryptoVault). Upgraded to dynamic multi-chain derivation using BIP-44 path segregation (m/44'/0'/0'/0/0 for BTC, m/44'/2' for LTC, m/44'/3' for DOGE, m/44'/60' for EVM, m/44'/195' for TRON, and m/44'/607'/0'/0'/0' for TON). Calculates generalized low-level Bech32 string formatting with dynamic HRP polynom inputs (bc / ltc). Manages BIP-39 mnemonic generation via window.crypto and PBKDF2/AES-256 local ledger encryption for localStorage.
* **js/app.js**: Core connection and UI event controller layer. Implements the global re-rendering state controller (window.WalletState.activeCoin). Intercepts clicks on the crypto cards to dynamically swap forms titles, button values, and visibility states (e.g., hiding the 1inch swap engine for non-EVM chains) without a single hardcoded line of HTML duplication.
* **js/security.js**: Active memory defense mechanism (SecurityLayer). Utilizes a dynamic wildcard query selector to automatically isolate and wrap all password fields (input[type="password"], #seedInput, and multi-stage unlock gates). Enforces credential input field masks, disables malicious data extraction (blocks copy, cut, and drag & drop events), and utilizes a safe microscopic timeout to erase sensitive credentials from the system clipboard instantly after a successful paste event.
* **js/utxo-vault.js**: Universal UTXO cryptographical execution layer (KryptidBitcoinEngine). Re-engineered into a parametrizabel, multi-network signing engine. Contains centralized in-memory network parameters (NETWORK_PARAMS) for Bitcoin, Litecoin, and Dogecoin. Dynamically injects magic bytes, specific fee bounds (e.g., 1 DOGE limit), dust limits (546 to 1000000 satoshis), maps localized private key hex string representations directly into bitcoin.Buffer.Buffer, signs multi-input transaction structures via localized bitcoin.TransactionBuilder, and routes raw transaction Hex strings to correct network Esplora API nodes.
* **js/ton-vault.js**: Production cryptographic layer for the TON ecosystem (KryptidTONEngine). Fully functional non-custodial signer leveraging standard BIP-44 key path derivation. Sells out an automated v4R2 client wallet construction method, calculates public keys through localized Ed25519 nacl signatures, formats robust Base64url user-friendly non-bounceable wallet address strings, and packages signed external transaction payloads to network node endpoints safely from RAM.
* **js/monero-vault.js**: Completed non-custodial Monero architecture layer (KryptidXMREngine). Designed to process dual-key stealth routing, separating Private Spend Keys and Private View Keys. Ready to construct RingCT cryptographic transaction bodies and sign ring structures locally in RAM. Active in the background but safely bypassed on the UI layer until a full production vendor/monero-core.js binary asset deployment is finalized in version v1.1.
* **js/blockchain.js**: Signed network service (BlockchainService). Holds the master architectural database (KryptidNetworkRegistry). Combines and fires live currency tickers in a single multi-currency API batch request (fsyms=BTC,LTC,DOGE,ETH,BNB,TRX,TON). Implements a polymorphic multi-chain loop that handles balance scanning for UTXO, EVM, TRON, and TON structures. Houses a multi-chain 1inch Token Balance API scanner (Ethereum Chain 1 / BSC Chain 56) and drives the decentralized 1inch Portal Router v6.0 with a persistent, locked 0.2% commercial referrer fee logic.
* **js/wallet-engine.js**: Multi-chain validation layer (WalletEngine). Upgraded to handle generalized transaction verification through validateTx(coin, target, amount). Enforces tight RegExp patterns across different universes (bech32 bc1/ltc1, legacy L/M/D/A, TRON capital T, and TON 48-character Base64url addresses). Acts as a catastrophic cross-contamination firewall—strictly blocking users from signing transaction structures if they mistakenly enter an address belonging to a foreign cryptographic family.

### 🛑 REUSE AND CODING RULES FOR FUTURE AI ASSISTANTS

1. **NEVER RE-INTRODUCE HARDCODED COIN LOGIC OR DUPLICATE BUTTONS**: The UI (#action-zone) and the networks logic (BlockchainService) are entirely data-driven and polymorphic. If a new coin needs to be added, it must be declared strictly as an entry in the existing configuration registries (KryptidNetworkRegistry in blockchain.js, NETWORK_PARAMS in utxo-vault.js, and deriveKeys in main.js). **Do not write new standalone event listeners, or new buttons for individual cointypes.**
2. **DO NOT ALTER MULTI-SEGMENT CONCAT SEQUENCE**: API connections use explicit multi-segment string concatenation to shield network paths from backend terminal mapping errors. Leave these string structures untouched.
3. **DO NOT INJECT STATE FRAMEWORKS OR NODE.JS BUILD TOOLS**: Keep the architecture purely frontend-driven, vanilla JavaScript, and low-level. No React, no Vue, no npm, no Webpack, no compilation. Everything must execute instantly inside an isolated NW.js/Edge DOM environment directly from raw client-side scripts.
4. **MAINTAIN POLYMORPHIC INTERFACES**: Every cryptographic vault family engine must expose identical execution signatures (deriveKeys / sendTransaction) so the orchestration layer in app.js and blockchain.js can call them dynamically using associative arrays (window[Kryptid${coin}Engine]).

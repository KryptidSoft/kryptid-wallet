### Kryptid Wallet (Multi-Chain Modular Edition)

Purely functional, client-side, non-custodial wallet for Bitcoin, Ethereum, Litecoin, Dogecoin, Binance Smart Chain, TRON, Toncoin, and Solana. Developed with zero cloud dependencies and no Node.js building tools using Notepad++ and PowerShell. Built on a data-driven, polymorphic architecture that categorizes assets into cryptographic families (UTXO, EVM, TRON, TON, SOL) to eliminate code duplication and scale infinitely without UI modifications.

### 🚀 CURRENT ARCHITECTURE & COMPONENT STATUS

* **index.html**: Production user interface in English. Built on a fully data-driven, state-reactive model using uniform `.crypto-card` blocks equipped with `data-coin` attributes (including newly added `SOL` card with dedicated `#solTokensContainer`). Contains a prominent visual legal Disclaimer, an alphabetical multi-fiat dropdown (11 currencies + physical gold XAU), a dynamic universal transaction form (`#action-zone`) with a single re-rendering button (`#universalSendBtn`), and a strict production Content Security Policy (CSP) expanded to cover active Web3 network RPC endpoints.
* **main.js (Root)**: Core cryptographic engine (CryptoVault). Manages dynamic multi-chain derivation using BIP-44 path segregation (`m/44'/0'/0'/0/0` for BTC, `m/44'/2'` for LTC, `m/44'/3'` for DOGE, `m/44'/60'` for EVM, `m/44'/195'` for TRON, `m/44'/607'/0'/0'/0'` for TON, and `m/44'/501'/0'/0'` for SOL). Calculates generalized low-level Bech32 string formatting with dynamic HRP polynom inputs (bc / ltc). Manages BIP-39 mnemonic generation via `window.crypto` and PBKDF2/AES-256 local ledger encryption for `localStorage`.
* **js/app.js**: Core connection and UI event controller layer. Implements the global re-rendering state controller (`window.WalletState.activeCoin`). Intercepts clicks on the crypto cards to dynamically swap forms titles, button values, responsive Base58/UTXO/hex placeholders, and visibility states (e.g., hiding the 1inch swap engine for non-EVM chains) without a single hardcoded line of HTML duplication.
* **js/security.js**: Active memory defense mechanism (SecurityLayer). Utilizes a dynamic wildcard query selector to automatically isolate and wrap all password fields (`input[type="password"]`, `#seedInput`, and multi-stage unlock gates). Enforces credential input field masks, disables malicious data extraction (blocks copy, cut, and drag & drop events), and utilizes a safe microscopic timeout to erase sensitive credentials from the system clipboard instantly after a successful paste event.
* **js/utxo-vault.js**: Universal UTXO cryptographical execution layer (KryptidBitcoinEngine). Re-engineered into a parametrizable, multi-network signing engine. Contains centralized in-memory network parameters (`NETWORK_PARAMS`) for Bitcoin, Litecoin, and Dogecoin. Dynamically injects magic bytes, specific fee bounds (e.g., 1 DOGE limit), dust limits, maps localized private key hex string representations directly into `bitcoin.Buffer.Buffer`, signs multi-input transaction structures via localized `bitcoin.TransactionBuilder`, and routes raw transaction Hex strings to correct network Esplora API nodes.
* **js/ton-vault.js**: Production cryptographic layer for the TON ecosystem (KryptidTONEngine). Fully functional non-custodial signer leveraging standard BIP-44 key path derivation. Spells out an automated v4R2 client wallet construction method, calculates public keys through localized Ed25519 nacl signatures, formats robust Base64url user-friendly non-bounceable wallet address strings, and packages signed external transaction payloads to network node endpoints safely from RAM.
* **js/solana-vault.js**: Dedicated cryptographic and tracking engine for the Solana ecosystem (KryptidSolanaEngine). Generates valid Solana Keypairs using the cryptographic curve Ed25519 from a 32-byte sliced BIP-39 seed. Signs native SOL transactions using standard `SystemProgram.transfer` instruction sets embedded with live RPC recent blockhashes. Features an isolated, non-blocking background SPL Token Scanner (`scanAndRenderTokens`) that fetches active public account states, cross-references contract mint addresses with the decentralized global Jupiter registry, and dynamically populates the UI with token tickers, balances, and asset icons.
* **js/blockchain.js**: Signed network service (BlockchainService). Holds the master architectural database (`KryptidNetworkRegistry`). Combines and fires live currency tickers in a single multi-currency API batch request (`fsyms=BTC,LTC,DOGE,ETH,BNB,TRX,TON,SOL`). Implements a polymorphic multi-chain loop that handles balance scanning for UTXO, EVM, TRON, TON, and SOL structures. Houses a multi-chain 1inch Token Balance API scanner (Ethereum Chain 1 / BSC Chain 56) and drives the decentralized 1inch Portal Router v6.0 with a persistent, locked 0.2% commercial referrer fee logic.
* **js/wallet-engine.js**: Multi-chain validation layer (WalletEngine). Handles generalized transaction verification through `validateTx(coin, target, amount)`. Enforces tight RegExp patterns across all active universes (bech32 bc1/ltc1, legacy L/M/D/A, TRON capital T, TON 48-character Base64url, and Solana 32-to-44 character Base58 addresses). Acts as a catastrophic cross-contamination firewall—strictly blocking users from signing transaction structures if they mistakenly enter an address belonging to a foreign cryptographic family.

### 🛑 REUSE AND CODING RULES FOR FUTURE AI ASSISTANTS

1. **NEVER RE-INTRODUCE HARDCODED COIN LOGIC OR DUPLICATE BUTTONS**: The UI (`#action-zone`) and the networks logic (`BlockchainService`) are entirely data-driven and polymorphic. If a new coin needs to be added, it must be declared strictly as an entry in the existing configuration registries (`KryptidNetworkRegistry` in `blockchain.js`, `NETWORK_PARAMS` in `utxo-vault.js`, and `deriveKeys` in `main.js`). **Do not write new standalone event listeners, or new buttons for individual cointypes.**
2. **DO NOT ALTER MULTI-SEGMENT CONCAT SEQUENCE**: API connections use explicit multi-segment string concatenation to shield network paths from backend terminal mapping errors. Leave these string structures untouched.
3. **DO NOT INJECT STATE FRAMEWORKS OR NODE.JS BUILD TOOLS**: Keep the architecture purely frontend-driven, vanilla JavaScript, and low-level. No React, no Vue, no npm (outside local asset extraction), no Webpack, no compilation. Everything must execute instantly inside an isolated NW.js/Edge DOM environment directly from raw client-side scripts.
4. **MAINTAIN POLYMORPHIC INTERFACES**: Every cryptographic vault family engine must expose identical execution signatures (`deriveKeys` / `sendTransaction`) so the orchestration layer in `app.js` and `blockchain.js` can call them dynamically using associative arrays (`KryptidSolanaEngine`, `KryptidTONEngine`, etc.).

### 📌 GUIDELINES FOR DESKTOP PACKAGING (.exe executable app via NW.js / Electron)

* **Architecture**: The desktop wrapper must be configured *offline-first* and leverage the current isolated sandbox.
* **Implementation**: Since the app already utilizes `package.json` for NW.js runtime configurations (enforcing charmed RAM isolation and blocking browser extensions/plugins via flags), packaging into an executable standalone `.exe` must be achieved using zero-dependency toolsets like `nwbuild` or raw binary resource hackers that wrap the existing `index.html`, `css/`, and `js/` directories into a single localized binary distribution without corrupting or breaking the internal `localStorage` PBKDF2/AES-256 client ledger mechanics.
* **Asset Integrity**: All vendor libraries (`crypto-js.min.js`, `ethers.umd.min.js`, `bitcoin.min.js`, `tonweb.js`, `solana-web3.min.js`) must remain embedded locally inside the folder structures to enforce absolute local execution.
